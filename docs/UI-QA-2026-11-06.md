## Narrow-screen reflow coverage (November 6, 2026)

[PR #14](https://github.com/GoreeCloud/maps/pull/14) adds synthetic Chromium layouts at 640px and 320px CSS widths, approximating the layout widths available when a 1280px display is reflowed at 200% and 400% zoom. The [passing branch browser run](https://github.com/GoreeCloud/maps/actions/runs/42298280672) exercises native keyboard tab activation across four panels, form-field and attribution reachability, and absence of document horizontal overflow. The resulting `reflow-200pct-equivalent.png` and `reflow-400pct-equivalent.png` screenshots were inspected: navigation and horizontally constrained controls appeared within the tested widths, with consent content scrollable at 320px.

**Limit:** Browser CSS viewport simulation is not native browser zoom. The screenshots do not establish full text scaling, all focus transitions, screen-reader support or GoreeCloud UI design acceptance.

## Genuine Chromium zoom findings (November 6, 2026)

- [PR #16](https://github.com/GoreeCloud/maps/pull/16) adopts the scoped isolated X11 zoom method from the Apache-2.0-licensed [GoreeCloud UI repository](https://github.com/GoreeCloud/gc-ui), not CSS transforms or a simulated 320px/640px viewport. **[Branch CI run 42303920433](https://github.com/GoreeCloud/maps/actions/runs/42303920433) passed** native zoom at both 200% (DPR 2, viewport 640×356 CSS px) and 400% (DPR 4, viewport 320×178 CSS px).
- Inspection of the original native-zoom screenshots exposed a real problem: almost only the header was captured at 400%, because viewport-fixed overlays and height constraints effectively hid the rest of the app. A targeted `max-width:700px` and `max-height:480px` CSS rule replaces the fixed-height mobile layout with ordinary document scrolling. On the corrected branch, document scroll heights of 976 and 1027 CSS px were observed at 200%/400%, and keyboard/geometry checks verified import control and attribution reachability without horizontal overflow.
- **Screenshot limitation:** the isolated GPU/Chromium screenshot at 400% after the fix yielded an all-dark frame despite successful DOM metrics and keyboard hit-target checks. The 200% capture was also visually incomplete. These screenshots are **not** proof of complete visual acceptance. Manual zoom, alternate browser engines and real assistive technology must be independently tested.

## Remaining quality gates

- Verify real geographic tiles, provider attribution, license compliance, and map-rendering performance before public hosting. The current community OSM tile URL is **development-only**, and search/routing services are disabled without operator configuration.
- Test actual Android and iOS browser devices, hardware-location permissions, pointer gestures and touch targets; the CI viewports simulate dimensions only.
- Conduct screen-reader review, full keyboard-only traversal, independent manual 200–400% zoom/reflow in multiple engines, accessible names and descriptions, contrast measurements across light/dark/high-contrast themes, and reduced-motion assessment.
- Integrate verified GoreeCloud UI design tokens/components and complete founder-required premium visual review across whole screens, focus/hover/error/loading states, and design-system acceptance.
- Do not infer safety-critical navigation capability, complete WCAG conformance, production deployment or MIPS/Anchor acceptance from these tests.

**Disposition:** Targeted P1 mobile layout findings corrected and verified under synthetic Chromium checks. Overall visual and accessibility acceptance remains **open**.
